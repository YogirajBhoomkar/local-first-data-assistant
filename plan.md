# Local-first desktop agent — Claude Code prompts, Phases 0 to 5

These prompts build an MVP of a desktop assistant that answers questions over large local files (CSV, Excel, Parquet, PDF, PPTX). Simple questions are handled on the user's machine by a small local model. Hard questions are escalated to a remote hosted LLM, and only the information that question needs is sent.

It is built in its own independent repo for now. The agent core is kept framework-light and behind clear interfaces, so it can later move into the BridgeAI Electron app.

## How to use these prompts

1. Create an empty folder for the new repo, run `git init`, and open Claude Code in it.
2. Paste **one phase at a time**, starting with Phase 0. Do not paste the next phase until the current one is reviewed and its tests pass.
3. Each phase works on its own local branch (`phase-0-bootstrap`, `phase-1-engine`, and so on) and is merged locally into `main` by you after review.
4. Optional: if you have a local clone of the Conversational BI repo, replace `<CBI_REPO_PATH>` in Phases 0 and 5 with its path. Claude Code will read it **as a reference only** to reuse the UI patterns and the streaming contract. If you do not have it, delete that line and the UI is built fresh.
5. After each phase, read `docs/phases/phase-N.md`, which Claude Code writes, before moving on.

### What each phase gives you

| Phase | Builds | You can check it by |
|---|---|---|
| 0 | Repo skeleton, rules, config, hardware probe, synthetic data, empty eval set | `npm run probe` prints a capability report; `npm test` is green |
| 1 | Local data engine on DuckDB: folder scan, file registry, schema profile, guarded read-only SQL | CLI answers SQL over a 2 to 5 GB synthetic file |
| 2 | Local and remote model adapters, hardware tiers, model benchmark | A benchmark report comparing Qwen 9B and Ministral 14B |
| 3 | Orchestrator, router, verification, privacy gate, escalation, egress log (tables) | CLI shows route, reasons and exactly what was sent |
| 4 | Documents path: PDF and PPTX text, chunks, keyword search, document escalation | CLI answers questions over sample PDFs and decks |
| 5 | Electron app, chat UI, privacy controls, packaging, full eval report, demo script | The desktop app runs the demo end to end |

## Rules for every phase (Claude Code must follow these)

Paste this block at the top of **every** phase prompt, or keep it in `CLAUDE.md` once Phase 0 has created it.

```
RULES FOR THIS REPO — follow them in every step

Git and safety
- Work only on the current local branch. Never push, never add a remote, never force anything.
- Commit in small steps with clear messages. Do not rewrite history.
- Never read, print, or create .env or .env.* files other than .env.example. Never print secrets, API keys, tokens, hostnames of private services, or user file paths in logs, tests or docs.
- Do not use real client names, real company data, or real people's names anywhere: code, comments, fixtures, test data, docs, commit messages. Use only synthetic data generated by our own scripts.

Privacy rules of the product (never weaken these to make something work)
- User files never leave the machine as whole files.
- Only the privacy gate module may build anything that goes to the remote model. No other module calls the remote model with data.
- Every remote call is written to the egress log before it is sent.
- If a step would need to break one of these rules, stop and report instead of working around it.

Engineering
- Node 22 (>= 22.13), TypeScript strict mode, ES modules, npm workspaces.
- Pin exact versions in package.json (no ^ or ~).
- Before using any library API, check it in the installed package's type definitions or its docs. Do not guess APIs from memory. If an API differs from what this prompt says, follow the real API and note the difference in the phase notes.
- Ask before adding a dependency that is large, native, or not named in the prompt.
- Keep the core logic free of Electron and UI code. Core talks to the outside only through the interfaces in packages/core/src/ports.
- Every new module gets unit tests (Vitest). Before you say a phase is done: typecheck, lint and all tests must pass.
- At the end of each phase write docs/phases/phase-N.md: what was built, decisions taken and why, how to run it, known gaps, and anything in this prompt that turned out to be wrong.
```

## Phase 1 — Local data engine (DuckDB)

```
[Paste the RULES block above first]

GOAL
Build the local data engine: scan a folder, register CSV, XLSX and Parquet files as queryable tables, profile their columns, and run read-only SQL safely with limits. No model yet. Everything in packages/engine, exposed to core through ports.

BRANCH
Create and switch to phase-1-engine from main (after Phase 0 is merged).

STEP 0 — LOOK BEFORE YOU BUILD
1. Read CLAUDE.md, docs/architecture.md and docs/phases/phase-0.md.
2. Check the current DuckDB Node client. Prefer the official "@duckdb/node-api" package. Confirm from its docs or types: how to open an in-memory database, run a query, stream or chunk results, interrupt a running query, and set options. Write what you found in the phase notes.
3. Check how this DuckDB version reads Excel: is the excel extension built in, or does it need INSTALL from the internet? Many corporate laptops block that. Test: can we load the extension from a file bundled with the app (offline)? Report the result before choosing (see STEP 4).
4. Check whether this DuckDB version supports the settings enable_external_access, allowed_directories (or allowed_paths) and lock_configuration. Report which exist.

STEP 1 — PORTS (in packages/core/src/ports)
- DataEnginePort:
    scanFolder(folder): Promise<FileEntry[]>
    registerFiles(entries): Promise<TableSchema[]>
    profile(tableName, options): Promise<ColumnProfile[]>
    runReadOnlySql(sql, limits): Promise<QueryResult>
    sampleRows(tableName, n, columns?): Promise<QueryResult>
    close(): Promise<void>
- Domain types (in core/domain), if not complete from Phase 0:
    FileEntry { id, alias, kind: "csv"|"xlsx"|"parquet"|"pdf"|"pptx"|"other", sizeBytes, modifiedAt, sheet? }
      alias is a safe short name like "policies" or "budget_plan"; the real path stays inside the engine and is never placed in model prompts or logs.
    TableSchema { tableName, fileAlias, columns: { name, type }[], rowCountEstimate }
    ColumnProfile { name, type, nullFraction, distinctEstimate, min?, max?, topValues? (max 5) }
    QueryResult { columns, rows, rowCount, truncated, elapsedMs }

STEP 2 — FOLDER SCAN AND FILE REGISTRY
- Scan one folder, not recursive by default (flag for one level deep). Ignore hidden and temp files (~$*.xlsx, .DS_Store).
- Detect kind by extension. PDF and PPTX are listed but not registered as tables (Phase 4).
- Build aliases: lower snake case of the file name, deduplicated with _2, _3. For each XLSX sheet: <file>_<sheet>.
- Keep a registry (in memory plus a small JSON file in cacheDir) keyed by path hash + size + modified time, so unchanged files are not re-profiled.

STEP 3 — TABLE REGISTRATION
- CSV: create a view per file using DuckDB's CSV reader with header and type auto-detection. Use sample-based detection; allow a config option to increase the sample size.
- Parquet: view per file.
- XLSX: see STEP 4.
- Table names are t_<alias>. The model will only ever see these names, never paths.

STEP 4 — EXCEL HANDLING
Excel files cannot hold more than about 1,048,576 rows per sheet, so they are usually far smaller than the multi-GB CSVs, but reading xlsx is slow. So convert each sheet once to Parquet in cacheDir and register the Parquet file.
- Option A (preferred if STEP 0 showed it works offline): DuckDB excel extension loaded from a bundled local file.
- Option B: a streaming xlsx reader in Node (choose a maintained one, tell me which and why, and pin it) that writes rows to a temporary CSV or directly into DuckDB, then COPY to Parquet.
Pick one, document why. Detect "messy" sheets: header not in row 1, merged cells, or mostly empty columns. In the MVP, do not try to fix them: register what you can, and attach a warning to the TableSchema that the agent can show the user ("this sheet has a title row above the header; results may be wrong"). Test with messy.xlsx from Phase 0.

STEP 5 — READ-ONLY SQL GUARD (most important part of this phase)
Model-written SQL must never be able to write, read other files, load extensions or change settings. Do it in two layers:
Layer 1, the engine settings, applied after all views are registered:
  - memory_limit and threads from config; temp_directory inside cacheDir so large queries can spill to disk
  - if supported (STEP 0): restrict file access to the selected data folder and cacheDir only, disable other external access, then lock the configuration so later SQL cannot change it
Layer 2, a statement check before execution:
  - exactly one statement; it must start with SELECT or WITH (after comments and whitespace are stripped)
  - reject keywords and functions anywhere outside string literals: INSERT, UPDATE, DELETE, CREATE, DROP, ALTER, COPY, ATTACH, DETACH, INSTALL, LOAD, PRAGMA, SET, RESET, CALL, EXPORT, IMPORT, CHECKPOINT, VACUUM, and file or network functions such as read_csv, read_csv_auto, read_parquet, read_json, read_text, read_blob, glob, and any http or s3 path
  - every table referenced must be one of the registered t_ names
  - use a real SQL tokenizer or parser if a maintained one supports the DuckDB dialect; otherwise a careful tokenizer that respects quotes and comments. Explain the choice.
Limits:
  - wrap the query to fetch at most maxResultRows + 1 rows, so we can set truncated = true
  - timeout: interrupt the query after queryTimeoutMs using the client's interrupt function (verify it exists); return a clear timeout error
  - return friendly error objects { code, message, hint } that the agent can use later: SYNTAX, UNKNOWN_TABLE, UNKNOWN_COLUMN, FORBIDDEN, TIMEOUT, TOO_LARGE, ENGINE
Tests: at least 25 guard tests, including tricky ones: keywords inside strings must be allowed, comments hiding a second statement, lower case and mixed case, CTEs, a semicolon followed by a second statement, read_csv inside a subquery, an unknown table, a quoted identifier that looks like a keyword.

STEP 6 — PROFILING
For each table: row count (exact for Parquet metadata, estimate otherwise unless cheap), per-column type, null fraction, distinct estimate (approx_count_distinct), min and max for numbers and dates, top 5 values for low-cardinality text columns. Profile on a sample for very large files (configurable, default 1,000,000 rows) and mark the profile as sampled. Cache profiles in the registry.

STEP 7 — CLI
Enable in apps/cli:
  cli files --folder ./sample-data          lists files, kinds, sizes, aliases, warnings
  cli schema --folder ./sample-data [--table t_x]   schema and profile
  cli sql --folder ./sample-data "SELECT ..."       runs guarded SQL and prints a table, row count, truncated flag and time

STEP 8 — PERFORMANCE CHECK
- Generate a 2 to 5 GB policies.csv with npm run gen:data.
- Script scripts/perf-engine.ts runs 6 queries (count, filter, group-by, top N, join with claims, date range) and records time and peak memory (process.memoryUsage plus DuckDB's own memory settings).
- Write results to eval/reports/engine-perf.md with machine info from the probe.
- If any query takes over 60 seconds or the process runs out of memory, report it and propose a fix (for example, converting large CSVs once to Parquet in cacheDir). Do not silently change limits.

DONE WHEN
- All tests pass, including the guard tests.
- cli sql works on the synthetic files, and the forbidden examples are rejected with clear errors.
- The perf report exists for at least one large file.
- docs/phases/phase-1.md covers the Excel choice, the guard design, the DuckDB settings found, and the perf results.
Commit and stop.
```

## Phase 2 — Local and remote model layer, hardware tiers, model benchmark

```
[Paste the RULES block above first]

GOAL
Connect the models through Mastra: a local model through an OpenAI-compatible endpoint (Ollama first), a remote hosted model through a configurable OpenAI-compatible or Azure OpenAI endpoint, and a mock model for tests. Pick the local model by hardware tier. Then build a benchmark that compares two local models on the simple table questions, so we decide with numbers.

The two candidate local models are Qwen3.5-9B and Ministral 3 14B.

BRANCH
phase-2-models from main.

STEP 0 — LOOK BEFORE YOU BUILD
1. Read CLAUDE.md, docs/architecture.md, docs/phases/phase-0.md and phase-1.md.
2. Install @mastra/core at exactly 1.32.1 (Node >= 22.13). Read its installed types and docs to confirm, and write in the phase notes:
   - how to define an Agent with instructions, a model and tools
   - how to define a tool with an input and output schema
   - how to plug in a model: which AI SDK provider packages it expects (for example an OpenAI-compatible provider), and which versions are compatible with Mastra 1.32.1
   - how streaming works (text deltas, tool calls, finish)
   Do not use the Mastra server or deployer for now; use @mastra/core as a library.
3. Check the real model tags:
   - Ollama library tags for Qwen3.5 9B and Ministral 3 14B (and their quantisation, for example q4_K_M). Confirm both exist. If a name differs from what I wrote, report it and use the real one.
   - Each model's license on its model card. Write it in the notes.
   - How to turn off "thinking" output for the Qwen model in Ollama (a request option or a prompt flag). Verify with one real call if Ollama is installed; otherwise note it as unverified.
   Replace <QWEN_9B_TAG> and <MINISTRAL_14B_TAG> in config defaults and .env.example with the confirmed tags.

STEP 1 — PORT
In core/ports: ChatModelPort with
   generate({ system, messages, tools?, responseSchema?, temperature, maxTokens, signal }) -> { text?, object?, toolCalls?, usage, latencyMs, modelId }
   stream(...) -> async iterable of { type: "text-delta" | "tool-call" | "finish" | "error", ... }
   health() -> { ok, modelId, detail }
The orchestrator in Phase 3 will use Mastra agents, but keep this port so tests and the benchmark can call models directly, and so core never depends on a specific SDK.

STEP 2 — ADAPTERS (packages/models)
- LocalOpenAICompatibleAdapter: baseUrl and model from config; default Ollama endpoint. Timeouts, one retry on connection error only (never on a 4xx). Sends the "thinking off" option where the model needs it.
- RemoteAdapter: provider "openai-compatible" (baseUrl, model, bearer key) or "azure-openai" (resource URL, deployment name, api-version, api-key header). Key from env only. Redact the key and the base URL in every log and error message.
  IMPORTANT: this adapter is only constructed inside the privacy gate (Phase 3). Export it from a path that the lint config forbids importing anywhere else (add an ESLint no-restricted-imports rule now, with a comment explaining why).
- MockModelAdapter: scripted responses keyed by prompt matchers, for tests.
- Also expose each adapter as a Mastra-compatible model object, so agents in Phase 3 can use them.
Tests: request shape for both providers, redaction, timeout, retry rules, mock matching.

STEP 3 — TIER SELECTION
packages/models/src/tier.ts: selectLocalModel(probeResult, config) -> { tier, model | null, reason }.
- Uses total RAM thresholds from config.localModel.tiers.
- If config.localModel.name is set, it wins (with a warning if RAM is below that tier's threshold).
- If Ollama is not reachable, or the chosen model is not installed, return tier "none" with a clear reason and the install hint (ollama pull <tag>), and the app runs in remote-only mode.
- Remote-only mode must still keep files local: the remote model gets only what the privacy gate allows, and DuckDB still runs all queries locally.
Tests for each branch.

STEP 4 — LOCAL TEXT-TO-SQL PROMPT
Write the prompt the local model uses for simple table questions (packages/agent/src/prompts/local-sql.ts). Input: the question, and a pruned schema (only the 5 to 12 most relevant columns per table, with types and a few top values). Output: strict JSON { sql, tables, confidence: 0..1, needsEscalation: boolean, reason }.
Column pruning: a deterministic function that scores columns by name and value overlap with the question (lower-case tokens, simple stemming, synonyms list in config). Always include id and date columns. Unit test it.
Keep the prompt short; small models do worse with long prompts. Include 3 short few-shot examples using the synthetic tables.

STEP 5 — BENCHMARK HARNESS
apps/cli: `cli bench --models <tag1>,<tag2> --runs 3 --folder ./sample-data`
For each model, for each SIMPLE table question in eval/questions.jsonl, 3 runs:
- call the local model with the local-SQL prompt
- run the returned SQL through the Phase 1 guard and engine
- compare with the expected result: run the reference SQL and compare result sets (order-insensitive unless the question asks for an order; numeric tolerance 1e-6)
Record per call: valid JSON, SQL passed guard, SQL ran, result correct, needsEscalation flag, confidence, latency, tokens.
Also run each HARD question once and record whether the model wrongly claimed it could answer (needsEscalation = false and the answer is wrong). That is the dangerous case.
Report to eval/reports/model-bench-<date>.md and .json:
- per model: accuracy on simple, SQL error rate, mean and p90 latency, wrong-confidence rate on hard, agreement between the 3 runs
- machine info from the probe at the top
- a short recommendation using this rule, written into the report before the numbers are computed: choose the 14B only if it is at least 10 points more accurate on simple questions AND its p90 latency is under 15 seconds on this machine; otherwise choose the 9B. If neither reaches 60% accuracy on simple questions, recommend remote-SQL mode (the remote model writes SQL from the schema; the local model only classifies and summarises).
The harness must run with the mock model in CI (no Ollama needed), and with real models when Ollama is available.

DONE WHEN
- Tests pass without Ollama.
- If Ollama and the models are available on this machine, a real benchmark report exists. If not, the notes say so and give me the exact commands to run it on another laptop.
- docs/phases/phase-2.md includes the Mastra API notes, the real model tags and licenses, the thinking-off method, and the benchmark result or instructions.
Commit and stop.
```

## Phase 3 — Orchestrator, router, verification, privacy gate, escalation, egress log (tables)

```
[Paste the RULES block above first]

GOAL
Build the full question-answering turn for TABLE questions: decide local or remote, try locally, verify, escalate through the privacy gate if needed, log every send, and return a streamed answer with a table and a chart spec. Expose it through one AgentContract so a host (CLI now, our Electron app later, another host app after that) can call it.

BRANCH
phase-3-orchestrator from main.

STEP 0 — LOOK BEFORE YOU BUILD
1. Read CLAUDE.md, docs/architecture.md and all phase notes. Read the benchmark report from Phase 2 and tell me which mode it recommends (local 9B, local 14B, or remote-SQL mode). Build all three; the mode is a config value: routing.mode = "local-first" | "remote-sql".
2. Check Mastra 1.32.1 workflows: can a workflow stream events from its steps while it runs? If yes, implement the turn as a Mastra workflow whose steps call plain functions in core. If streaming from workflows is awkward, implement the turn as a plain TypeScript orchestrator in packages/agent that calls Mastra agents, and explain the choice. Either way the logic of each step lives in tested core functions.

STEP 1 — THE AGENT CONTRACT
In core/ports: AgentContract
   card(): { name, version, description, capabilities: string[], dataPolicy: string }
   ask({ turnId, question, history: { role, text }[] (last N turns, default 3), context: { folderSelected: boolean } }, signal) -> AsyncIterable<TurnEvent>
TurnEvent types (reuse the shape of the reference project's streaming contract if Phase 0 found one; otherwise use these):
   trace       { step, status: "start"|"done"|"skip"|"error", detail }   human-readable progress lines
   route       { route: "local"|"remote", layer, reasons: string[] }
   egress      { egressId, destination: "remote-model", summary }        emitted BEFORE a send
   confirm     { egressId, preview }                                     only when confirmBeforeSend is on; the host replies through a confirm(egressId, approved) method
   text        { delta }
   text-reset  {}
   final       { answer, table?: QueryResult, chart?: ChartSpec, sql?: string[], route, filesUsed: string[] }
   suggestions { items: string[] }  up to 3 follow-up questions
   error       { code, message }
Also add confirm(egressId, approved) to the contract.
ChartSpec: { type: "bar"|"line"|"pie"|"scatter"|"table", x, y, series?, title } — kept simple and chosen deterministically from the result shape (dates -> line, one category + one number -> bar, few categories share -> pie only if <= 6 slices and the question asks for share). Unit test the chooser.

STEP 2 — ROUTER (core/routing)
Decide in layers and record every reason. Config routing:
   mode: "local-first"
   maxColumnsLocal: 40
   maxFilesLocal: 1
   escalateKeywords: ["why", "explain", "forecast", "predict", "recommend", "compare to last", "trend", "insight", "root cause"]
   typeRoutes: { lookup: "local", filter: "local", aggregate: "local", groupby: "local", topn: "local", chart: "local", join: "remote", explain: "remote", other: "remote" }
   maxLocalAttempts: 2
   requireAgreement: true
Layers in order:
   1. Policy: if remoteModel.enabled is false or no remote is configured, route is always local; if the question is hard, answer what we can and tell the user what we could not do.
   2. Hard rules (no model): number of tables the question needs (matched by the column pruner), total columns in scope, escalate keywords.
   3. Question type: the local model classifies into exactly one of the typeRoutes keys, output strict JSON { type, confidence }. Make this a QuestionClassifier port with two implementations: RuleClassifier (keywords only) and LocalModelClassifier. Leave a clearly marked stub DecisionModelClassifier for a small decision model (for example Laya) that we may evaluate later; do not install it now.
   4. Try locally (only if layers 1 to 3 say local): the local model writes SQL (Phase 2 prompt), the engine runs it.
   5. Verify: the SQL passed the guard, ran without error, finished before the timeout, returned at least one row, the result is not all null, the model's confidence is >= 0.6, and, if requireAgreement, a second generation at a slightly higher temperature returns the same result set (compare a hash of sorted rows). Each failed check is a reason.
   6. Fallback: on a failed check, retry once with the error message added to the prompt; if it fails again, escalate.
In remote-sql mode, skip 3 to 5 for SQL: the remote model writes SQL from the schema, and the local side runs and verifies it.
RouteDecision { route, layer, reasons[], attempts } is attached to the final event. Unit test every layer with the mock model, including: simple question stays local; join escalates at layer 2; "why" escalates at layer 2; low confidence escalates at layer 5; disagreement escalates; remote disabled keeps it local and returns a partial answer with a clear message.

STEP 3 — PRIVACY GATE (core/privacy + packages/agent/src/gate)
The only code allowed to construct the RemoteAdapter (lint rule from Phase 2).
Input: an EscalationRequest { purpose: "write-sql" | "answer-from-results" | "answer-from-chunks", question, history, tables?, results?, chunks? }
Output: an EscalationPacket that is exactly what will be sent, plus a summary.
Rules for tables:
   - never send file paths or real file names; only aliases and t_ table names
   - "write-sql" sends: question, short history, pruned schema (column names and types) for the tables in scope; plus, if tabularLevel >= "aggregates", the column profiles (null fraction, distinct counts, min, max, top values); plus, if tabularLevel = "rows", up to 20 sample rows per table to show value formats
   - "answer-from-results" sends the local query results the answer needs, only if tabularLevel = "rows", capped at maxRowsSent and maxBytesSent. If the result is bigger, send a locally computed summary (aggregates by the main dimensions) instead, and say so in a trace event. If tabularLevel is lower, the remote model never sees values: the local side writes the answer from a template plus the local model.
   - denyColumns are removed everywhere; maskColumns values are replaced with stable tokens (HMAC with a per-install random key kept in cacheDir; the key never leaves the machine). Tokens are mapped back locally before showing the answer.
   - a whole file is never sent, in any mode. Add a test that builds a packet from a 100k-row result and asserts it is within limits.
Before sending: write the egress record, emit the egress event, and if confirmBeforeSend, emit confirm and wait (with a 5-minute timeout that cancels the send).

STEP 4 — EGRESS LOG
Append-only JSONL in cacheDir/egress.log.jsonl. Each record: egressId, turnId, timestamp, destination, purpose, privacy level, tables and columns sent, row count, byte size, SHA-256 of the exact payload, approved by user (yes/no/auto), and the outcome (sent, cancelled, failed). Store the full payload only if config privacy.logFullPayload is true (default false), and even then only locally. Add `cli egress --last 20` to print it. Tests: a record is written before the network call (assert with the mock), cancelled sends are logged, the API key never appears.

STEP 5 — ESCALATION FLOWS (tables)
   A. Remote writes SQL: gate sends "write-sql"; the remote model returns strict JSON { sql: string[] (max 3 queries), explanation }. Each query goes through the Phase 1 guard and runs locally. On an error, one repair round: the gate sends the SQL and the error message (no data) back.
   B. Remote writes the answer: only when the question needs reasoning over the values (explain, why, compare, insight) and the policy allows it. The gate sends "answer-from-results".
   C. Otherwise the answer is written locally: by the local model from the result if a tier is available, or by a deterministic template ("There are 1,234 open policies in EMEA") if not.
Prompts for the remote model live in packages/agent/src/prompts/remote-*.ts; keep them short and state clearly that the model gets schema and results, not files.

STEP 6 — FOLLOW-UPS AND HISTORY
- Up to 3 follow-up suggestions, generated by the local model if available (else by the remote model only if policy allows sending the question; else none). They must only use tables and columns that exist.
- History: the last N turns' question and answer text are passed to the router and to the prompts; no result rows from earlier turns are resent.

STEP 7 — CLI
   cli ask --folder ./sample-data "question"       streams trace, route and reasons, egress summary (with a y/n prompt when confirmBeforeSend), the answer, the table, the chart spec and the SQL
   cli ask --explain-route                          prints only the routing decision without running anything remote
   cli eval --folder ./sample-data                  runs all table questions end to end and writes eval/reports/e2e-<date>.md: accuracy, local share, remote share, bytes sent per question, wrong-local count, and p50 and p90 time

DONE WHEN
- All tests pass with the mock models.
- cli ask works end to end with the mock remote and, if available, the real local model.
- The e2e report exists (mock or real) and lists, for every question, the route, reasons and exactly what was sent.
- docs/phases/phase-3.md explains the workflow-vs-orchestrator choice, the routing config, the privacy levels and the egress log format.
Commit and stop.
```

```
[Paste the RULES block above first]

GOAL
Answer questions over local PDF and PPTX files. Extract text locally, split it into chunks, build a local keyword index, find the most relevant chunks for a question, and either answer locally or escalate with only the question and the top chunks. No OCR, no images, no embeddings in this phase.

BRANCH
phase-4-documents from main.

STEP 0 — LOOK BEFORE YOU BUILD
1. Read CLAUDE.md, docs/architecture.md and all phase notes.
2. Choose and confirm (from docs and types) a maintained library for each, pin it, and write the choice and reason in the notes:
   - PDF text per page in Node (for example pdfjs-dist or a wrapper around it). It must run offline and without a browser.
   - PPTX: a PPTX is a zip of XML files. Use a zip reader and an XML parser to read slide text (a:t elements in ppt/slides/slideN.xml) and speaker notes (ppt/notesSlides). Keep slide order from ppt/presentation.xml.
   - Keyword search: a small in-process full-text library with BM25-style ranking (for example MiniSearch), so we do not depend on a DuckDB extension that may need internet.
3. Generate synthetic fixtures with a script (scripts/gen-docs.ts): 3 PDFs (a 20-page made-up "underwriting guidelines" document, a 5-page made-up "quarterly summary", and one scanned-style PDF that is an image only, to test the no-text case) and 2 PPTX decks (10 slides each, with titles, bullets, a table and speaker notes). All content is invented. Keep the committed fixtures under 2 MB; larger ones are generated into sample-data/.

STEP 1 — PORTS AND TYPES
In core: DocumentStorePort
   index(entries: FileEntry[]) -> { indexed: number, skipped: { alias, reason }[] }
   search(query, { topK, aliases? }) -> Chunk[]
   getChunk(id) -> Chunk
Chunk { id, fileAlias, kind: "pdf"|"pptx", location: { page? , slide? }, title?, text, charCount, score? }

STEP 2 — EXTRACTION AND CHUNKING (packages/docs)
- PDF: text per page; join lines sensibly; drop repeated headers and footers (lines that appear on more than 60% of pages). If a page has under 20 characters, mark it as "no text"; if more than 80% of pages have no text, skip the file with reason "scanned PDF, OCR not supported in MVP".
- PPTX: one unit per slide: title + body text + table cell text + notes (prefixed "Notes:").
- Chunking: about 800 tokens per chunk (estimate tokens as chars / 4), 100-token overlap, never split inside a slide if the slide fits, keep page or slide numbers on each chunk.
- Cache extracted chunks in cacheDir keyed by path hash + size + modified time, like Phase 1.
- Limits: skip files over a configurable size (default 200 MB) with a clear reason.

STEP 3 — INDEX AND SEARCH
- Build the keyword index over chunks (title boosted x2), persist it in cacheDir, rebuild only for changed files.
- search returns topK chunks with scores. Add a simple relevance check: if the best score is below a configurable threshold, or no query word appears in any chunk, return an empty result with reason "no relevant content found".

STEP 4 — ROUTING AND ANSWERING FOR DOCUMENTS
Extend the router (Phase 3) with document questions:
- The question goes to the documents path if the user's selected files include PDF or PPTX and the question does not name a table, or if the classifier returns type "document". Add "document" to the classifier types. Mixed questions (needing both tables and documents) are routed "remote" with reason "mixed sources" in the MVP, and the gate sends top chunks plus schema only.
- Local answer: if a local tier is available and the question is a lookup ("what does the guideline say about X", "which slide mentions Y") and the top chunks fit in 6,000 characters, the local model answers from the chunks with citations [file alias, page or slide].
- Escalate: if the question asks for a summary across many documents, a comparison, or reasoning, or if the local answer fails a check (no citation, cites a chunk it was not given, or says it cannot find it while the score is high), escalate.
- Privacy gate, purpose "answer-from-chunks": sends only the question, short history, and the top docTopK chunks, capped at docMaxChars, with file aliases and page or slide numbers. Never the whole document. Same egress logging and confirm flow as tables. Add a test that a 200-page document never produces a packet over the cap.
- The final event carries citations: { fileAlias, page? , slide?, snippet (max 200 chars) } so the UI can show where the answer came from.

STEP 5 — EVAL AND CLI
- Add 15 document questions to eval/questions.jsonl (kind "doc"): 8 lookups (simple), 7 summaries or comparisons (hard), with "contains" expectations (key phrases that must appear) and the expected citation.
- cli ask works for document questions and prints citations.
- cli eval includes document questions and reports retrieval hit rate (did the expected page or slide appear in the top K), answer pass rate, local share, and characters sent.

DONE WHEN
- Tests pass, including the scanned-PDF skip, the header and footer removal, the PPTX notes, and the packet cap.
- cli ask answers the synthetic document questions with citations.
- docs/phases/phase-4.md lists the library choices, the chunking rules, the routing rules for documents, and the eval numbers.
Commit and stop.
```
